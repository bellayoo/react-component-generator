# Commit

변경사항을 분석해 컨벤션에 맞는 한국어 커밋으로 남긴다. 별도 승인 절차 없이 분석 후 바로 커밋한다.

## 절차

### 1. 변경사항 분석
- `git status`로 변경·추적되지 않는 파일을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 내용을 읽는다. 파일명만 보고 판단하지 않는다.
- 저장소가 아니면(`not a git repository`) 중단하고 사용자에게 알린다.
- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.

### 2. 논리적 단위로 분류
- 하나의 커밋은 하나의 목적만 담는다. 목적이 다른 변경(예: 기능 추가 + 의존성 정리)은 나눈다.
- 같은 목적에 속한 파일(컴포넌트, 스타일, 테스트)은 한 커밋으로 묶는다.
- 파일 하나 안에서 목적이 섞였다면 `git add -p`가 필요한지 사용자에게 먼저 묻는다(대화형 플래그는 이 환경에서 쓸 수 없다).
- 커밋하면 안 되는 파일은 제외하고 알린다: `.env`, API 키·토큰·자격 증명, `node_modules`, `dist`, 임시 파일.

### 3. 커밋 메시지 작성 (한국어)
형식: `타입: 요약`

| 타입 | 용도 |
|------|------|
| feat | 사용자에게 보이는 기능·화면 추가나 변경 |
| fix | 버그 수정 |
| refactor | 동작은 그대로인 구조·코드 개선 |
| chore | 빌드, 설정, 의존성, 문서 등 기타 작업 |

- 요약은 50자 안팎, 마침표 없이, "무엇을 했는지"를 명사형 또는 `~추가`, `~수정`처럼 간결하게 쓴다.
- "왜"가 diff만으로 드러나지 않으면 빈 줄 뒤 본문에 1~3줄로 덧붙인다.
- 최근 `git log --oneline -10` 스타일이 이미 있으면 그에 맞춘다.
- 예: `feat: 결과 창에 폴더 탭과 상태바 추가`, `fix: API 키 미설정 시 오류 배너가 뜨지 않는 문제 수정`

### 4. 커밋
1. 커밋 단위마다 해당 파일만 `git add <파일>`로 스테이징하고 `git commit`을 실행한다. `git add -A`나 `git add .`는 쓰지 않는다.
2. 끝나면 `git log --oneline`으로 결과를 보여주고, 만든 커밋별 메시지와 제외한 파일(이유 포함)을 요약해 알린다.

## 하지 않는 것
- `--no-verify`, `--amend`, force 옵션을 임의로 쓰지 않는다. 훅이 실패하면 원인을 고치고 새 커밋으로 만든다.
- 푸시하지 않는다. 요청이 있을 때만 별도로 한다.
