# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"로 처리하지 않는다.

## 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)**이다. 프로젝트 규칙이 없는 항목에만 적용한다.

## 적용 기준

### TDD 필수

- **비즈니스 로직**
- **API** (라우트 핸들러, 외부 API 호출 래퍼, 에러 매핑)
- **유틸리티 / 순수 함수**
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성한다)

### TDD 불필요

- **타입 정의** (`type`, `interface`)
- **설정 파일** (`tsconfig`, `vite.config`, `eslint.config` 등)
- **순수 UI** (로직 없는 마크업·스타일)
- **SQL** (스키마, 마이그레이션)

경계가 모호하면(UI 안에 분기·상태 로직이 있는 경우 등) **로직 부분을 분리해 TDD를 적용**한다.

## RED - GREEN - REFACTOR 사이클

### 1. RED

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 담지 않는다.
- 테스트를 **반드시 실행**해서 **실패를 눈으로 확인**한다. 실행 없이 실패를 가정하지 않는다.
- 실패 이유는 **"기능 미구현"**이어야 한다. 문법 오류, import 오류, 오타, 잘못된 설정으로 인한 실패는 RED가 아니다. 고친 뒤 다시 실행한다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다. 테스트를 수정한다.

### 2. GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI:** 지금 테스트가 요구하지 않는 분기, 옵션, 추상화, 일반화를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두** 실행해 전부 통과하는지 확인한다.

### 3. REFACTOR

- **중복 제거, 이름 개선, 헬퍼 추출**만 한다.
- 매 변경 후 테스트를 실행해 **green을 유지**한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED로 간다.

### 4. 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제**하고 **RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지**한다. 주석 처리, 임시 파일, 복사해 두기 모두 포함한다. 보고 베끼면 테스트가 코드에 맞춰진다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트가 불필요하다" | 단순한 코드는 테스트도 30초면 쓴다. 단순하다는 판단이 가장 흔한 회귀의 출발점이다. 적용 대상이면 예외 없다. |
| "나중에 테스트를 추가하겠다" | 나중에 쓴 테스트는 구현에 맞춰 작성되어 버그를 못 잡는다. 대부분은 쓰이지도 않는다. 지금 RED부터 시작한다. |
| "시간이 없다" | 테스트 없는 코드의 디버깅과 회귀 수정이 더 오래 걸린다. 시간이 없을수록 사이클을 지킨다. |
| "삭제하면 낭비다" | 이미 쓴 코드는 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 더 크다. 삭제하고 테스트부터 다시 쓴다. |
| "프로토타입이다" | 프로토타입은 코드가 아니라 학습이 목적이다. 그 코드를 유지·배포할 계획이라면 프로토타입이 아니다. 버릴 코드만 예외이며, 버리지 않는 순간 TDD 대상이 된다. |
